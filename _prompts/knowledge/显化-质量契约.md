# 显化质量契约

> create_spec / audit_spec 落盘前须满足本文 Q 项。思维与口径见各 command 第 1 步（第一性原理、对抗性审查、PRD 与 knowledge 边界）。

## A. spec 落盘（需求显化）

### 原 Skill §6 验收标准（DoD — Definition of Done）

### 6.1 SQL 设计验收

- [ ] 执行前已查阅项目内 SQL 设计相关文档或 Skill，并浏览存量表结构
- [ ] 所有候选表均已判断新建/复用
- [ ] 每张表均有 DDL 和表意图说明
- [ ] 字段命名风格与存量表保持一致，主键使用雪花 ID，未出现自增主键示例
- [ ] 审计字段口径与项目一致：`create_time`、`create_by`、`update_time`、`update_by`、`delete_time`、`delete_by`；时间为 `datetime(3)`，默认 `CURRENT_TIMESTAMP(3)` / `ON UPDATE CURRENT_TIMESTAMP(3)`
- [ ] `delete_time` 删除时间字段已正确添加，注释统一为`删除时间`
- [ ] 有持久化时已输出查询–索引对照简表（或明确「不涉及」）；列表/条件查询已写清过滤、排序、分页方式
- [ ] 未在显化阶段臆造 QPS/表行数/方法并发强度作为「已确认」事实（规模与并发由显化审核阶段 0 分轴采集）
- [ ] 本库/能力方案：对**明显需要并发设计**的导出方法或能力流程，已注明并发契约（可并发 / 须串行 / 流程级互斥 / `⚠️ 待确认`）；非明显需要的不强制填写
- [ ] 有 Consumer/cron 等非 HTTP 调度时，已点名处理函数或流程名（供审核第二轴识别）；未将其表述为 HTTP 接口

### 6.2 领域设计验收

- [ ] 已明确判断新领域/已有领域
- [ ] 新领域已完整定义边界（含排除项）
- [ ] 已有领域已说明归属理由及边界影响
- [ ] 无循环依赖领域关系

### 6.3 领域模型验收

- [ ] 每个核心概念已定义 **Model**（`.../model/*Model`），字段及含义清晰
- [ ] Model 默认贫血；若设计了 Model 行为方法，已说明理由，且不访问 Repository、不跨 Model 编排
- [ ] 每张表已定义 **Entity**（`.../entity/*Entity`，`extends BaseEntity` 等与 DDL 一致）
- [ ] Entity 使用 `@TableField` / `@TableName`；禁止把持久化注解写在 Model 或 Request/Response 上
- [ ] API 已定义对应 **Request/Response**（`{Action}Request` / `{Action}Response`）
- [ ] 已定义 DomainService/Impl 与 DomainRepository/Impl；UseCase 未直调仓储
- [ ] DomainRepositoryImpl 使用 `MyBatisDao`；写操作经 **DomainService** 进入闭包；`@Transactional` 落点与 spec 一致（写用例默认 `execute`）
- [ ] 若需求涉及持久化，已说明 Repository 的 SQL 依赖与缓存策略，且查询谓词与 §3.1 查询–索引对照一致
- [ ] 仅在需求确有异步要求时，才补充事件结构草稿

### 6.4 领域方法清单验收

- [ ] 第九章仅列领域层方法，未混入 UseCase/Request
- [ ] 每个方法已标明变更类型（新增/修改/删除）
- [ ] 每个方法已标明是否写数据；写数据方法已在 §3.4.2 Step 1 决策表中有对应行
- [ ] 每个方法已说明设计原因和大致内容
- [ ] 方法清单与后续交互流程中出现的方法一一对应，无遗漏

### 6.5 用例（UseCase）与跨边界编排验收

- [ ] 符合 §3.4.1（用例表、`execute`、第十章幂等/事务落点、非 HTTP 触发方式）

### 6.5.1 事务与一致性验收

- [ ] 符合 §3.4.2（Step 1 决策表完整；Step 2 闭包/跨边界；见 `Java事务与一致性规范.md`）
- [ ] 第十章写用例「事务」列与第十一章 Step 1 表逐写动作一致（无双源冲突）

### 6.6 交互流程验收

- [ ] 领域写接口在 spec 中成对列出 正向接口/补偿接口，未设计编排方直调或未写回退路径
- [ ] 域内每个关键动作均有独立交互组，步骤完整
- [ ] 域内写操作交互组组首已复述事务决策，并含 `@Idempotent`/`@Transactional` 进入点与闭包范围（与第十章一致）
- [ ] 第十二章以 UseCase 为入口，经 DomainService→DomainRepository，非 Controller/UseCase 直调 Mapper
- [ ] 每一步都已标注数据形态（Request/Response、基础类型、Model、Entity）
- [ ] 跨域写交互组已含步骤顺序、成对正向/补偿（多服务时含 URL）、补偿快照与非 DB 副作用归属
- [ ] 跨域交互均已标注参与领域
- [ ] 若存在异步交互，已说明事件结构和幂等策略；若涉及消费/定时管道且明显有并发诉求，已点名处理函数或流程；若无异步需求，已明确说明无需设计事件流
- [ ] 无遗漏的跨领域调用，且未出现 SQL 相关对象跨领域传递

### 6.7 Controller 入口与 API 设计验收

- [ ] 所有 HTTP 接口均已列出
- [ ] spec 已写「本项目结构约定」且 API 路由列完整 URL（`{context-path 或网关前缀}/v1/...`，`context-path 或网关前缀` 按端配置），与 Controller 相对路径 + `context-path 或网关前缀` 口径一致
- [ ] 接口主输入符合 [JavaWeb与API规范](../knowledge/JavaWeb与API规范.md) §3（默认推荐 POST+JSON Body）
- [ ] 每个接口已写明路由、入口 Controller、接口作用说明
- [ ] 每个接口已说明请求 Body 参数、权限要求与入口端归属（按 `context-path 或网关前缀` / 端别）
- [ ] 每个接口标注调用的 **UseCase** 方法
- [ ] 跨上下文接口已说明 UseCase 内调用顺序与数据拼装逻辑
- [ ] 所有响应均经 Response 适配设计（经 `Response.success`/`@Valid @RequestBody`），未出现裸对象；**未把预制 Response 字段写成强制全站契约**
- [ ] 每个接口已说明关键失败路径、失败语义与哨兵落点；权限类码由业务在 `BizException.errorCode` 中定义；未把技术异常写成前端契约
- [ ] Controller 层未包含业务逻辑，只承担请求接入与经 `Spring MVC Controller` → Response 的协议适配
- [ ] Controller 实现优先通过 `@Valid @RequestBody` / `Response.success` / `Response.success(page)` / `Response.fail / BizException` 收口，未重复手写样板或绕过 Response
- [ ] Controller 通过 `@RequestMapping 路径` 注册路由，由 `Spring @RequestMapping` 统一收口
