## 1. 目标

- **做什么**：将产品给出的一段需求描述，整理为结构化、单文档的原始需求显化文档
- **为什么**：产品需求通常以用户故事或非技术语言描述，开发人员需要二次解读，容易产生理解偏差；本 Skill 通过标准化流程消除歧义，先沉淀一份足够完整的技术需求原文，再交给后续 spec 工作流工具继续拆解和推进
- **不做什么**：
  - 不负责编写具体代码实现
  - 不负责输出 `tasks.md`、`checklist.md` 等执行态文档
  - 不负责维护任务状态、验收状态、执行证据与自动验收结果
  - 不负责输出 UI 设计稿、原型图或视觉规范（文字描述的 UI 说明属于需求文档范围）
  - 不负责性能压测方案
  - 不负责部署与运维方案

### 架构与 boot 契约（贯穿全文）

> **业务分层、包名、模块划分**不在母版中定死：须结合业务工程现有代码；在 spec **「本项目结构约定」**（见输出模板 §2.3）中写明。下列仅为使用 **yomi-boot-java** 时的集成底线。

- **数据访问**：符合 [Java数据访问规范](../knowledge/Java数据访问规范.md)（Repository/Mapper 边界、SQL 安全）
- **事务与跨边界**：符合 [Java事务与一致性规范](../knowledge/Java事务与一致性规范.md)（无 DTM；跨边界写须补偿或最终一致）
- **HTTP/API**：符合 [JavaWeb与API规范](../knowledge/JavaWeb与API规范.md)（`Response` / `BizException`）
- **组件选型**：符合 [基础库能力索引](../knowledge/基础库能力索引.md)
- **boot 仓**：`yomi-boot-java` 根目录仅 `component-*` 与 `qucik-starter` **组件集成测试**，**禁止**写入产品领域逻辑；**不得**将 `qucik-starter` 的 Controller→Repository 等写法当作业务分层样板（见 [基础库能力索引](../knowledge/基础库能力索引.md)）

**分层（清洁架构 + DDD-light，spec §2.3 须落地）**：

> 用例类 `*UseCase` 放在 **`{product}-usecase`**。领域类型在 **`{context}-domain-api`**，实现在 **`{context}-domain`** / **`{context}-infrastructure`**。本库经 `*DomainService`；缓存等经 domain-api 端口（如 `*CachePort`）。

**调用链（强制）**：

```text
Controller → UseCase → DomainService → DomainServiceImpl → DomainRepository → DomainRepositoryImpl → DB
```

| 类型 | 命名示例 | 职责 |
| ---- | -------- | ---- |
| `*Controller` | `ConfigController` | HTTP、`Response<T>`；只调用 `*UseCase` |
| `*UseCase` | `PageConfigUseCase` | 对外 **`execute`**；编排 `*DomainService` / `*Helper` / domain-api **端口**；跨域编排仅在本层 |
| `*Helper` | `ConfigHelper` | `{product}-usecase` 内映射与组装；无 `@Transactional` |
| `*DomainService` / `*DomainServiceImpl` | `ConfigDomainService` | 单领域；本域 `*DomainRepository`；领域规则；**领域内** `@Transactional` 按需（spec 写明） |
| `*DomainRepository` / `*DomainRepositoryImpl` | `ConfigDomainRepository` | Model↔Entity、持久化 |

Maven：**`adapter-web` → `usecase` → `{context}-domain-api` ← `{context}-domain` + `{context}-infrastructure`**。usecase 不依赖 infrastructure。

### 3.0 需求澄清（前置步骤）

**目标**：在进入任何设计章节之前，识别需求描述中的模糊点，避免基于不确定前提做出错误设计。

**执行规则**：

- 通读产品需求，识别以下类型的模糊点：
  - **缺少边界条件**：如"刷新缓存"——是刷新全部配置缓存，还是仅刷新当前配置项？
  - **缺少状态定义**：如"公告可下线"——哪些状态下允许下线，是否允许重复下线？
  - **缺少异常路径**：如"删除角色前需解绑资源组"——若角色仍绑定用户或资源组，接口如何处理？
  - **缺少关键规则**：如"系统参数支持缓存"——更新配置后是立即清理缓存，还是由后台手动刷新缓存？
- 对每个模糊点，用 `⚠️ 待确认` 标记并列出备选假设，然后**选取最合理的假设继续执行，不阻塞后续设计**
- 所有待确认项汇总在需求显化文档的最前面，供产品/开发确认

**若需求清晰无歧义**：跳过本步骤，直接进入 §3.1。

### 3.1 SQL 表结构设计

**目标**：为本次需求涉及的持久化数据给出完整的 DDL，并说明每张表的设计意图。

**执行步骤**：

1. **识别实体**：从需求描述中提取所有需要持久化的概念（名词），列出候选表清单

2. **加载数据库设计规范**：在正式设计之前，必须加载 §2.2 知识文档依赖中声明的《数据库表设计规范》，**完整阅读**后再进行设计，以确保与项目已有规范保持一致。若需求涉及缓存方案，同时加载《Redis设计规范》

3. **参考已有 DDL**：优先查看 `sql/ 或 src/main/resources/db/` 目录下的存量表结构，掌握表名前缀、审计字段、枚举字段、索引命名习惯，标记哪些候选表与存量表重合（复用）、哪些需要新建

4. **设计字段与索引**：结合第 2、3 步获取的规范与风格，完成每张表的字段设计和索引设计

5. **输出 DDL 与设计意图**：以标准 `CREATE TABLE` SQL 块输出，每张表后附一段**表意图说明**（2-5 句话），解释该表存储什么数据、服务哪个业务场景、与哪些表存在关联

6. **输出查询–索引对照（仅当有持久化或查库时）**：针对本需求**高频或列表类**查询（通常对应后续核心读路径），输出简表：`查询场景 / Repo 方法（可暂定）| 过滤·排序·分页字段 | 依赖索引（已有或拟建）| 备注`。条件不明时标 `⚠️ 待确认` 并给合理假设，**不得省略该对照表**。无持久化且无查库则**整步跳过**，不得为凑格式编造对照表。

7. **若无新增表**：若需求不涉及新建表（仅修改已有表字段，或无需任何持久化变更），在本章输出：
   - `本需求不涉及新增表结构`，并简述原因
   - 若涉及**已有表字段变更**，列出变更清单：`表名 | 字段名 | 变更类型（新增/修改/删除）| 变更说明`
   - 若仍有对已有表的查询变更，仍应输出第 6 步对照表；若完全无持久化/无查库，写明「本需求不涉及查询–索引对照」

**输出格式示例**：

```sql
-- 系统配置表：存储后台可维护的 KV 配置项
CREATE TABLE `t_config` (
  `id` bigint NOT NULL COMMENT '主键ID',
  `config_key` varchar(100) NOT NULL COMMENT '配置键',
  `config_value` varchar(500) NOT NULL COMMENT '配置值',
  `description` varchar(255) DEFAULT NULL COMMENT '配置描述',
  `create_time` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
  `create_by` bigint DEFAULT NULL COMMENT '创建人ID',
  `update_time` datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
  `update_by` bigint DEFAULT NULL COMMENT '更新人ID',
  `delete_time` datetime(3) DEFAULT NULL COMMENT '删除时间',
  `delete_by` bigint DEFAULT NULL COMMENT '删除人ID',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_config_key` (`config_key`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='系统配置表';
```

> **表意图说明**：`t_config` 表用于承载后台管理可维护的系统参数，配置键全局唯一，供业务模块按键读取。审计字段遵循项目统一审计字段口径，删除状态通过 `delete_time` 判定。若需求涉及配置缓存，本表仍只存储持久化数据，缓存策略应在 Repository 实现或组件层单独说明。

**查询–索引对照**（示例）：

| 查询场景 / Repo 方法 | 过滤·排序·分页 | 依赖索引 | 备注 |
| -------------------- | -------------- | -------- | ---- |
| 后台按键模糊分页 `PageList` | `config_key LIKE`、`delete_time IS NULL`；`id DESC` 分页 | `uk_config_key`（等值更优）；模糊前导 `%` 时可能难用索引 | 后台低频可接受；若升为高频需评估 |
| 按主键 `FindByID` | `id`、软删 | `PRIMARY` | — |

### 3.2 业务领域判断与定义

**领域判断标准（内置规范）**：

> 领域是一组具有统一业务语义和清晰边界的业务能力集合。判断依据：**同一领域内的概念彼此强内聚，跨领域的概念彼此弱耦合**。

**判断步骤**：

1. **提取核心概念**：从需求中提取 3-5 个核心业务名词（如：系统配置、配置缓存、公告发布、角色资源组）
2. **识别已有领域**：优先结合 业务工程可部署单元目录（惯例示例 `com.{company}.{product}.{module}/`）模块结构识别现有**各领域服务**，通常应先判断是否归入仓库中已存在的业务域（**示例域**：以项目现有域为准，勿把示例名写成强制适用范围）
3. **匹配度判断**：逐一对比核心概念与已有领域职责，若 **超过 60% 的核心概念** 落在某已有领域的职责范围内，则归属该领域；否则判断为新领域
   - **特殊情形**：若核心概念均匀分散至多个已有领域（如概念 A 属于领域 X、概念 B 属于领域 Y，无任何一个领域超过 60%），则以**主要业务能力**所在领域为归属判断依据（业务能力数量最多的领域），若确实无法判断，直接定义为新领域并在文档中标注 `⚠️ 待确认`
4. **若是新领域**，执行 §3.2.1
5. **若属已有领域**，执行 §3.2.2

#### 3.2.1 新业务领域定义

当需求引入全新的业务概念、无法归入已有任何领域时，必须完整定义新领域：

| 输出项 | 说明 |
| ------ | ---- |
| **领域名称** | 中文业务名 + 英文标识符（如：订单领域 `order`） |
| **领域职责** | 该领域负责管理哪些核心业务概念（2-4 句话描述） |
| **领域边界—包含** | 列出该领域内的所有业务能力（功能列表） |
| **领域边界—排除** | 明确列出哪些相关但不属于本领域的概念 |
| **对外契约** | 向其他模块暴露的 **`*DomainService` 接口**（Model 进/出，同进程默认）；HTTP 由 `adapter-web` + `{product}-usecase` 承担；**多服务**时再写对外 HTTP API |
| **依赖领域** | 本领域依赖哪些其他领域（允许单向依赖，禁止循环依赖） |

**输出格式示例**：

```
### 新领域定义：{领域中文名}（{domainKey}）

**职责**：
- 管理 {核心业务对象} 的完整生命周期
- 对外暴露 {关键业务能力}，供上层 **UseCase** 编排时注入本域 **`*DomainService`**

**边界—包含**：
- {能力点 1}
- {能力点 2}
- {能力点 3}

**边界—排除**：
- 不负责 {应由其他已有领域承担的职责 1}
- 不负责 {应由其他已有领域承担的职责 2}

**对外契约**（供其他 UseCase 注入编排）：
- `{DomainKey}DomainService#getById(...)`、`{DomainKey}DomainService#bind(...)` 等（Model 进 Model 出）

**依赖领域**：{如有依赖则列出；若无则写“无”}
```

#### 3.2.2 归属已有领域说明

当需求属于已有领域时，必须明确说明：

| 输出项 | 说明 |
| ------ | ---- |
| **归属领域** | 领域名称 + 英文标识符 |
| **归属理由** | 从业务职责角度说明为什么属于该领域（3-5 句话） |
| **对已有边界的影响** | 是否需要扩展该领域的边界？如需扩展，列出新增的业务能力 |
| **不归属其他领域的理由** | 如有可能混淆的领域，逐一说明为何不属于那些领域 |

### 3.3 领域模型定义

> 对象命名见 [Java数据访问规范](../knowledge/Java数据访问规范.md) §3、[JavaWeb与API规范](../knowledge/JavaWeb与API规范.md) §2.3。**本章只写 domain 侧**（`{context}-domain-api` / `{context}-domain` / `{context}-infrastructure` 等 **Maven 模块**），不写 Request/Response、不写 UseCase（其在 `{product}-usecase` 模块）。

**Model 建模口径**（DDD-light，默认贫血）：

- **默认贫血**：不变量与同聚合多步规则收口在 `*DomainServiceImpl`（经 `*DomainService` 接口暴露）
- **按需充血**：复杂状态机/多分支不变量可在 Model 上内聚方法；不得访问 Repository、不得跨聚合编排
- **领域服务**：方法签名使用 **Model / 基础类型**，禁止 `*Request`/`*Response`

**执行步骤**：

1. 定义 **Model** 与**不变量表**（唯一键、状态、删除约束等）
2. 在 **`{context}-domain-api`** 定义 **`*DomainRepository` 端口**（返回/接收 Model）
3. 在 **`{context}-infrastructure`** 定义 **Entity** + Mapper（详见 DDL 章）
4. 在 **domain-api** 定义 **`*DomainService` 接口**；在 **`{context}-domain`** 定义 **`*DomainServiceImpl`**（只依赖本域 `*DomainRepository`）
5. 在 **infrastructure** 定义 **`*DomainRepositoryImpl`**（Model↔Entity、调用 Mapper）
6. **Request/Response** 与 **用例 `*UseCase`** 在 **`{product}-usecase` 模块** / spec §10 写，不在本章展开

**输出格式示例**：

**业务 Model**（模块 `config-domain-api`，包路径以 spec §2.3 为准）

```java
@Data
public class ConfigModel {
    private Long id;
    private String configKey;
    private String configValue;
    private String description;
}
```

**领域服务接口**（模块 `config-domain-api`）

```java
public interface ConfigDomainService {
    ConfigModel create(ConfigModel draft);
    ConfigModel getById(Long id);
    Page<ConfigModel> page(ConfigQuery query, Pageable pageable);
}
```

**领域服务实现**（模块 `config-domain`）

```java
@Service
@RequiredArgsConstructor
public class ConfigDomainServiceImpl implements ConfigDomainService {
    private final ConfigDomainRepository configDomainRepository;

    @Override
    public ConfigModel create(ConfigModel draft) {
        // 唯一性等领域不变量；再 configDomainRepository.save(draft)
    }
    // ...
}
```

**仓储端口**（模块 `config-domain-api`）

```java
public interface ConfigDomainRepository {
    ConfigModel save(ConfigModel model);
    Optional<ConfigModel> findById(Long id);
    Page<ConfigModel> page(ConfigQuery query, Pageable pageable);
}
```

**表 Entity**（模块 `config-infrastructure`，含 `ConfigMapper`）

```java
@TableName("t_config")
@Data
public class ConfigEntity extends BaseEntity {
    private String configKey;
    private String configValue;
    private String description;
}
```

> `ConfigDomainRepositoryImpl` 仅在 **`config-infrastructure`** 模块；usecase 模块通过 domain-api 依赖，**不**直接依赖 infrastructure。

**缓存等非 DB 端口**（模块 `config-domain-api`，由 infrastructure 实现）

```java
public interface ConfigCachePort {
    void rebuild();
}
```

### 3.4.1 用例（UseCase）与跨边界编排

**目标**：列出全部 **用例 `*UseCase`**（Request/Response）；单用例可只编排一个 `*DomainService`，跨领域用例在同一 UseCase 内编排**多个** `*DomainService`。

**规则**：

| 项 | 要求 |
| -- | ---- |
| 入口 | 一个 HTTP/调度动作 → 一个 `*UseCase`；对外方法统一 **`execute`**（类名表达语义） |
| 依赖 | UseCase 注入 `*DomainService`、`*Helper`、domain-api 端口；不注入其他 UseCase、不直调 `*DomainRepository`/Mapper |
| 跨域 | 同一 UseCase 内编排多个 `*DomainService`；多服务/事件见 spec §2.3、§3.6 |
| 复用 | 多 UseCase 共享逻辑放在 `*Helper`（映射/组装，无事务、不跨域编排） |
| 幂等与事务 | 写用例默认 `@Transactional` + `IdempotencyUtils` 幂等闭包都在 **`execute`**（幂等入口只有 `IdempotencyUtils`）；领域内事务仅在 spec 写明时标在 `*DomainServiceImpl` 写方法（见 [Java事务与一致性规范](../knowledge/Java事务与一致性规范.md) §2.1） |
| 非 HTTP | cron/MQ 等调用同一 `*UseCase#execute`；第十章注明触发方式 |

**事务列**（写用例必填，顺序同 §3.4.2）：

**输出格式示例**：

| 类型 | 方法 | 输入 | 调用的领域内能力 | 输出 | 事务（先决策 → 再边界） |
| ---- | ---- | ---- | ---------------- | ---- | ----------------------- |
| 用例 | `CreateConfigUseCase#execute` | `CreateConfigRequest` | `ConfigDomainService#create` | `CreateConfigResponse` | 开本地 DB；`REQUIRED`；`@Transactional` 在 `execute`，幂等闭包 `IdempotencyUtils.execute(...)` 在其内（默认） |

| 用例 | `DeleteRoleUseCase#execute` | `DeleteRoleRequest` | `RoleDomainService#delete` | `Void` 或空 Response | 开本地 DB；`REQUIRED`；`@Transactional` 在 `execute`（默认） |

    private final ConfigHelper configHelper;

    @Transactional(rollbackFor = Exception.class)

                    return configHelper.toCreateResponse(saved);
                });
    }
}

### 3.4.2 事务与一致性设计

**目标**：对**所有写数据动作**按两步法设计——**先**决策「是否开本地 DB 事务」与传播关系（知识库 §3），**再**写闭包/编排——避免未决策就画闭包或只写「需要事务」。完整约束以 `Java事务与一致性规范.md` 为准。

**何时必须输出本章**：只要需求包含任一写数据动作（领域 DB 写、跨域写、多表写、写后改缓存/发通知等副作用涉及持久化或跨模块状态变更），就必须输出；若全需求均为纯读，写「本需求无写数据动作，无需事务与一致性设计」并简述原因。

**强制顺序（两步法）——不得颠倒**：

```text
Step 1  写动作事务决策（每个写数据动作一行）
        ↓ 是否写数据？是否开本地 DB 事务？传播关系（§3）？
Step 2  事务边界设计（仅对「开本地 DB 事务」的动作展开）
        ↓ 闭包内外、跨边界步骤与补偿、Controller 入口、幂等、禁止项
```

#### Step 1：写动作事务决策（先做）

**覆盖范围**：每一个写数据动作，包括 **UseCase 写用例**（含跨上下文编排）、仓储多表写、以及 Redis/消息等副作用。**领域 DomainService 若仅做校验不写库，单独一行标「不写 DB」。** 漏列视为未完成显化。

每个写动作必须先回答：

| 决策项 | 可选值与含义 |
| ------ | ------------ |
| 是否写数据 | 是 / 否（否则本行写「无需事务」并停止，不进入 Step 2） |
| 是否开启本地 DB 事务 | **开**：对外写用例默认在 `*UseCase#execute`；领域内或被调写 API 按需标在 `*DomainServiceImpl`；幂等入口（`IdempotencyUtils`）与 spec 对齐；**不开**：编排方不写本库或无 DB 副作用，须写明理由 |
| 传播关系 | 见 [Java事务与一致性规范](../knowledge/Java事务与一致性规范.md) **§3**（与「是否开本地 DB 事务」分列填写）；**禁止**假设 HTTP 能加入本服务本地 Spring/JDBC 事务 |

**Step 1 输出表示例**：

| 写动作 | 所在层 | 写的资源 | 是否开本地 DB 事务 | 传播关系（§3） | 决策理由 |
| ------ | ------ | -------- | ------------------ | -------------- | -------- |
| 创建配置 | `CreateConfigUseCase#execute` | `t_config` | 开 | `REQUIRED` | 单域单表写 |
| 删除角色 | `DeleteRoleUseCase#execute` | 角色表+绑定表 | 开 | `REQUIRED` | 同库多表原子 |
| 分配角色（同库原子） | `AssignRolesUseCase#execute` | 主体+角色绑定同库 | 开 | `REQUIRED` | 同库跨域；`@Transactional` 在编排方 `execute` |
| 角色模块被调删除 | `RoleDomainServiceImpl#delete`（被调方写 API） | 角色表+绑定表 | 开 | `跨边界无 DB 传播` | 编排方无共享 DB；`@Transactional` 在 spec 第十章写本方法；多服务时再写对外路由 |
| 分配角色（编排无本库写） | `AssignRolesUseCase#execute` | 多域 + token | 不开 | `编排方无 DB 事务` | 编排方不写本库；下游各域或 HTTP 各自事务/补偿 |
| 撤销 token | 副作用步骤 | Redis token | 不开 | `无 DB 事务` | 不进 DB 闭包；编排成功后再执行 |

> **同库跨域原子写**：多个 `*DomainService`、**同一数据源**，应在编排 `*UseCase#execute` 开 `REQUIRED`（`@Transactional` 默认落点），勿误用「编排方无 DB 事务」。后者用于编排方**不写本库**或下游为 **跨边界无 DB 传播**（被调方在 `*DomainServiceImpl` 开事务）。
>
> Step 1 **未完成前，禁止进入**闭包步骤表、跨边界补偿/最终一致表等边界设计。

#### Step 2：事务边界设计（后做）

凡 Step 1「是否开本地 DB 事务」= **开** 的写动作（含传播 `跨边界无 DB 传播` 的被调方），须展开闭包与幂等；传播为 `编排方无 DB 事务` 的编排方 UseCase只写步骤顺序与补偿，不写 DB 闭包。

1. **原子性与闭包边界**：对外写用例默认 **`@Transactional` 在 `*UseCase#execute`**，闭包内经 **DomainServiceImpl → DomainRepositoryImpl → DB**；Redis/HTTP/缓存失效/token 等 **不进** DB 闭包（若在 `execute` 内编排，须在事务提交后执行，如闭包外步骤、`afterCommit`）；领域内事务按 spec 标在 `*DomainServiceImpl` 时适用该层闭包
2. **跨边界写**（UseCase 用例）：分支顺序、正向/补偿**成对能力**（多模块单体写 `XxxUseCase#execute`；**多服务**时再写成对 URL）、补偿快照；编排方 **不**实现对方领域状态恢复
3. **Controller 入口**：调 UseCase；领域对外写 API 成对正向/补偿；禁止绕过 UseCase 直调 DomainRepository/Mapper
4. **幂等分工**：`IdempotencyUtils` 幂等键与 **DB 唯一索引** 分工（见 `Java事务与一致性规范.md` §4），不得互相替代
5. **禁止项自检**：无直调写、无闭包内 Redis/HTTP/MQ 等外部 IO、补偿方法不得再查外服务、无 **未经 spec 第十章** 在 `*DomainRepositoryImpl` 或写路径 Service 上私自 `@Transactional`（**允许**：spec 写明的 `*DomainServiceImpl` 领域内落点）、无「外部 HTTP 加入本地事务」的假设

#### 闭包内外边界（对应 Step 1 中「开事务」的行）

| 写动作 | 闭包内（本地 DB） | 闭包外 / 独立分支 |
| ------ | ----------------- | ----------------- |
| 删除角色 | `DeleteRoleUseCase#execute`（含绑定清理） | token 撤销在闭包外或编排 UseCase 步骤 |
| 更新配置 | `UpdateConfigUseCase#execute` | 缓存失效（`外部在事务外`） |

#### 跨边界步骤与补偿（若适用）

| 顺序 | 领域/副作用 | 正向能力 | 补偿能力 | payload / 快照字段 |
| ---- | ----------- | -------- | -------- | ------------------ |
| 1 | 角色域 | `RoleDomainService#delete`（多服务时可映射为 HTTP 路由） | `RoleDomainService#deleteCompensate` | 幂等键、`previousRoleIds` 等 |
| 2 | token 撤销 | （编排 UseCase 本地或独立步骤） | （对应补偿或空操作说明） | subjectId 列表 |

### 3.5 单上下文用例内交互流程

> **单上下文**指同一限界上下文内一次 **UseCase 用例** 的执行链，不是跨模块「编排」。
> 默认链路：**Controller → UseCase → DomainService → DomainServiceImpl → DomainRepository → DomainRepositoryImpl → DB**。

**执行规则**：

- 每个 **UseCase 用例** 一个交互组；**用例入口**写 `*UseCase#execute`，不写 HTTP 路径
- 跨上下文能力在 §3.6，本章只写本域 UseCase→DomainService 链
- 步骤须经过 **Request → Model →（领域规则）→ Entity**，禁止 UseCase 直写 SQL
- 需标明每一步的数据形态（Request/Response、基础类型、Model、Entity）
- 需标明校验点：Request 入参校验（UseCase）、领域不变量（DomainService）
- **写操作交互组强制步骤**（缺任一项视为未完成显化）：
  0. 组首标明 Step 1 决策结论：是否写数据、是否开本地 DB 事务、传播关系（§3，与 §3.4.2 Step 1 表一致）

  3. 持久化步骤写明 **DomainRepositoryImpl** 经 `MyBatisDao`/`Mapper` 在同一事务内写库

### 3.7 Controller 入口与 API 设计

> Controller 只做协议适配，**只调 `*UseCase`**（含跨上下文用例）；鉴权由 `component-token` / `component-rbac` 完成。统一返回 `Response<T>`。


> **HTTP 出口**以 [JavaWeb与API规范](../knowledge/JavaWeb与API规范.md) 为准：Controller 返回 `Response<T>`；分页使用 `PageResponse`；业务失败使用稳定 `errorCode`。

**执行规则**：

- 列出本次需求涉及的所有 HTTP 接口
- 每个接口明确标注：HTTP 方法、路由、入口 Controller、请求参数、认证/权限、调用的 **UseCase#execute**、响应数据来源
- 若接口跨多个上下文，说明编排 **UseCase** 内调用的各 **`{Domain}DomainService`** 顺序与 Model 拼装（多服务时补充远程集成）
- Controller 只调用 **UseCase**，不把 `HttpServletRequest` 传入内层；客户端 IP 等放在 Request 字段
- 对外 HTTP 路由在 spec API 章节写**完整 URL**（`context-path 或网关前缀` + `/v1/{资源}/{动作}`）；跨模块写由编排方 **UseCase** 触发；本服务被调写接口须成对列出正向/补偿路径（见 Java事务 §5.2）
- **仅含单个 id 字段的请求结构体统一命名为 `{Action}Request`**（如 `GetConfigDetailRequest`），不创建 `IdDTO` 等公共 DTO
- **分页**：业务 `PageXxxRequest` 内嵌 `page`/`pageSize`（或组合框架 `PageRequest`）；出参 `PageResponse<XxxResponse>`
- 响应输出：单条 `Response.success(data)`；分页 `Response.success(PageResponse)`；失败 `Response.fail(errorCode)` 或 `BizException`（见 [JavaWeb与API规范](../knowledge/JavaWeb与API规范.md)）
- 每个接口至少说明成功路径与关键失败路径；预期业务失败须写出稳定字符串 `code`（如 `USER_NOT_FOUND`）及哨兵落点（`BizException` / 库内 / `BizException.errorCode`）
- 仅将用户可见的业务失败、参数校验失败写入接口错误语义；内部技术异常只说明统一兜底为 `INTERNAL_ERROR`（`INTERNAL_ERROR`），不把堆栈或口语化细节写成前端契约
- 若需求涉及前端国际化，应参考 （本母版不含前端规程），在 API 章节说明 errorCode：前端只按 `code` 做 i18n，**禁止**消费响应 `msg`

**输出格式示例**：

| HTTP 方法 | 路由（示例：`context-path 或网关前缀`=`/{endpoint}/api`） | 入口 Controller | 接口说明 | 请求参数 | 权限要求 | 关联 UseCase | 响应组装说明 | 错误码说明 |
| --------- | ---- | --------------------- | -------- | -------- | -------- | ------------ | ------------ | ---------- |
| `POST` | `{context-path 或网关前缀}/v1/config/query` | `ConfigController` → `PageConfigUseCase` | 后台分页查询系统配置 | `PageConfigRequest` | 入口端已登录（**示例**） | `PageConfigUseCase#execute` | `Response.success(pageConfigUseCase.execute(req))` | 参数错误走 `@Valid` |
| `POST` | `{context-path 或网关前缀}/v1/config/detail` | `ConfigController` → `GetConfigDetailUseCase` | 按 ID 查询详情 | `GetConfigDetailRequest` | 入口端已登录（**示例**） | `GetConfigDetailUseCase#execute` | `Response.success(getConfigDetailUseCase.execute(req))` | `CONFIG_NOT_FOUND` |
| `POST` | `{context-path 或网关前缀}/v1/config/cache/refresh` | `ConfigController` → `RefreshConfigCacheUseCase` | 手动刷新缓存 | `{}` | 入口端已登录（**示例**） | `RefreshConfigCacheUseCase#execute` | `Response.success()` | 内部失败兜底 |

**Controller 注册示例**（`ConfigController.java`）：

```java
@RestController
@RequestMapping("/v1/config")
@RequiredArgsConstructor
public class ConfigController {
    private final PageConfigUseCase pageConfigUseCase;
    private final GetConfigDetailUseCase getConfigDetailUseCase;
    private final RefreshConfigCacheUseCase refreshConfigCacheUseCase;

    @PostMapping("/query")
    public Response<PageResponse<ConfigResponse>> page(@Valid @RequestBody PageConfigRequest req) {
        return Response.success(pageConfigUseCase.execute(req));
    }

    @PostMapping("/detail")
    public Response<GetConfigDetailResponse> detail(@Valid @RequestBody GetConfigDetailRequest req) {
        return Response.success(getConfigDetailUseCase.execute(req));
    }

    @PostMapping("/cache/refresh")
    public Response<Void> refreshCache() {
        refreshConfigCacheUseCase.execute();
        return Response.success();
    }
}
```
