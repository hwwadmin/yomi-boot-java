# 质量文档生成

---

## 0. 基础信息

- **Skill 名称**: 质量文档生成
- **描述**: 基于已闭合的 `spec.md`（及可选 PRD）生成测试用例文档与产品验收文档，落盘到业务工程 `_quality-doc/{YYYYMMDD}_{需求名称}/` 下的 `test.md` 与 `accept.md`；与 `check_code` 同为可选质量侧产物，不由 `do_spec` 触发
- **作者**: zwei
- **创建日期**: 2026-07-27

---

## 关联知识库

- **按需**：`knowledge/JavaWeb与API规范.md`（第十四章 API 与 `Response`/`errorCode` 口径）

## 1. 目标

- **做什么**：读取 `_feat-doc/{YYYYMMDD}_{需求名称}/spec.md`（及可选 `_doc/*-prd.md`），按本 Skill 的派生规则与输出骨架，在 `_quality-doc/{YYYYMMDD}_{需求名称}/` 下生成 `test.md`（测试用例）与 `accept.md`（产品验收）
- **为什么**：开发主闭环（显化 → 审核 → 落地）不产出面向测试与产品的可执行文档；本 Skill 补齐协作侧输入，使测试与验收口径与已审需求一致，且不污染 `spec.md`
- **不做什么**：
  - 不修改 `spec.md` / `audit.md` / `tasks.md`，不编写业务代码
  - 不替代开发侧 TDD 单测与 HTTP 集成测试，不跑 `check_code`
  - 不维护执行态回写（通过率、证据落点、自动验收命令）；结果勾选栏留空由人填写
  - 不调度其他 Agent；本 Skill 为独立规则集，由 command 触发执行

## 2. 输入/依赖

### 2.0 调用方式与输入

调用本 Skill 时，需指定已审核闭合的 `spec.md` 路径。Agent 以该文档为主要输入，按需读取同需求 PRD，按 §3 派生两份质量文档并落盘。

> 示例调用：「请使用质量文档生成 Skill，基于 `_feat-doc/20260604_系统参数管理/spec.md` 生成质量文档」

可选补充：

> `需求来源：_doc/20260604_系统参数管理-prd.md`

### 2.1 前置 Skill 依赖

| 名称 | 状态 | 说明 |
| ---- | ---- | ---- |
| 需求显化 | 已发布 | 本 Skill 消费 `spec.md`：**第十章**用例表（`*UseCase#execute`）、**第十四章** HTTP、第十一章事务/一致性、场景与异常章 |
| 显化审核 | 已发布 | **建议**在 `audit.md` 无未闭合严重项后生成；本 Skill 不强制读取 `audit.md`，但须在输入中确认 spec 已与审核结论对齐 |

### 2.2 知识文档依赖

| 文档 | 关联点 | 说明 |
| ---- | ------ | ---- |
| spec §2.3 | 测试边界 | `test.md` 为产品验收向用例，不替代 `mvn test` / HTTP 集成测试 |

`spec.md` 章节结构对照前置 Skill「需求显化」；生成时以 spec / PRD 业务与契约描述为准，不展开技术实现方案。无其他强制知识依赖。

## 3. 技术方案

### 3.1 执行流程概览

```text
确认 spec.md（及可选 PRD）路径
  │
  ▼
阶段 1：收集上游口径（§3.2）
  │  提取范围/非目标、业务规则、关键场景、异常路径、对外接口、验收相关表述
  │
  ▼
阶段 2：派生测试用例（§3.3）
  │  按硬约束生成 TC，覆盖正常 / 异常 / 边界；写路径补一致性场景
  │
  ▼
阶段 3：派生产品验收条目（§3.4）
  │  以 PRD 验收标准 + spec 范围/规则为主，生成可勾选 AC
  │
  ▼
阶段 4：落盘 test.md + accept.md（§4）
  │
  ▼
阶段 5：自检（§6 验收标准）
```

### 3.2 阶段 1：收集上游口径

**目标**：建立可追溯的派生来源清单，禁止发明未在上游出现的需求点。

**必读**：

- `spec.md`：范围与非目标、业务规则与关键场景、关键异常路径；**第十章**全部 `*UseCase`（含非 HTTP「触发方式」行）；**第十一章**写路径与补偿（若有）；**第十四章** Controller/API（路由 ↔ UseCase）；产品 UI 说明（若有）；风险与待确认项
- `_doc/*-prd.md`（若存在）：业务目标、功能需求、业务规则、验收标准

**规则**：

- 仅归纳上游已确认内容；假设与待确认项须在文档中显式标记，不得写成已确认事实
- 目录名优先与 `_feat-doc/{YYYYMMDD}_{需求名称}/` 对齐，写入 `_quality-doc/{YYYYMMDD}_{需求名称}/`
- 若目标 `test.md` / `accept.md` 已存在，先读取现有内容，按用户意图覆盖重写或增量修订，保留仍有效条目

### 3.3 阶段 2：派生测试用例（`test.md`）

**目标**：产出测试人员可执行的用例文档，口径对齐 spec，不写实现方案。

**派生硬约束**（缺一不可，否则 DoD 不通过）：

| 上游来源 | 最少产出 |
| -------- | -------- |
| spec **第十章**每一行用例（含跨上下文、非 HTTP） | ≥ 1 条用例；**关联**须写 `*UseCase#execute`；HTTP 再写第十四章路由 |
| 每个关键场景（spec §4.2） | ≥ 1 条正常用例（可与用例行合并，但须能追溯到场景） |
| 每个关键异常路径（spec §5） | ≥ 1 条异常用例 |
| 每个对外**写**接口（第十四章） | 成功 + 参数校验失败 + 业务失败（若 spec 有对应 `errorCode`） |
| spec **第十一章**事务 / 第十三章跨边界补偿或最终一致 | ≥ 1 组一致性 / 补偿或部分失败场景；事务用例与 spec 落点一致（写路径默认 `*UseCase#execute`） |

**单条用例必含字段**：

| 字段 | 说明 |
| ---- | ---- |
| TC-ID | 如 `TC-001`，同文档内连续唯一 |
| 优先级 | P0 / P1 / P2 / P3 |
| 类型 | 正常 / 异常 / 边界 |
| 前置 | 账号、数据、环境前提 |
| 步骤 | 可逐步执行 |
| 期望结果 | 可观察结果；业务可见错误码/文案须写出 |
| 关联 | spec **第十章** `*UseCase#execute`；HTTP 补 **第十四章** 路由/`errorCode`；非 HTTP 写触发方式；可选 PRD 条目 |

**禁止**：

- 把集成测试代码、`mvn test`、覆盖率要求写入正文作为主内容
- 要求修改业务代码才能完成文档
- 把建议级优化写成阻塞测试项

### 3.4 阶段 3：派生产品验收条目（`accept.md`）

**目标**：产出产品可勾选的验收单，使用产品语言，不以测试步骤为主。

**派生规则**：

- 优先消费 PRD「验收标准」；无 PRD 时从 spec 范围、业务规则与关键场景收敛为可观察通过标准
- P0 能力须能追溯到 spec **第十章** `*UseCase#execute` 或 PRD 功能条；HTTP 交付在 **第十四章** 可演示
- 复述非目标，防止范围漂移
- 待确认项不得伪装为已验收通过项；未关闭的写入「已知限制与延期项」

**单条 AC 必含字段**：

| 字段 | 说明 |
| ---- | ---- |
| AC-ID | 如 `AC-001`，同文档内连续唯一 |
| 业务表述 | 产品语言描述交付点 |
| 通过标准 | 可观察、可判定；禁止「系统正常」等空泛表述 |
| 演示路径 | 1～3 步页面或主流程说明 |
| 关联 | PRD 章节；可选 spec 第十章 `*UseCase#execute`、第十四章路由；可选 `TC-ID` |

**建议闭合口径**（写入文档供人使用，AI 不代填结论）：

- 所有 P0 的 AC 通过
- 非目标中的能力未被误交付
- 待确认项已关闭或已登记为已知限制

### 3.5 与可选巡检的关系

- 本 Skill 与 `check_code` / 代码巡检**互不前置、互不触发**
- 不读取 `_ipc-doc/` 作为生成输入

## 5. 约束与规范

- 产物必须落在工程根 `_quality-doc/{YYYYMMDD}_{需求名称}/`，不得写入 `_feat-doc/`、`_task-doc/`、`_ipc-doc/` 或 `_prompts`
- 同轮必须同时产出 `test.md` 与 `accept.md`，不得只交一份
- 不得把 `TC-ID` / `AC-ID`、勾选状态、验收结论写回 `spec.md`
- 不得由本 Skill 触发 `do_spec` 或 `check_code`
- 不得编造上游未出现的功能点；缺口标记为待确认或已知限制
- 定稿前删除模板痕迹、空占位章节标题堆砌与无关示例
- 路径、需求名称与 `_feat-doc` 目录语义对齐；文档编号与元信息表完整

## 6. 验收标准（DoD）

### 6.1 路径与文件

- [ ] 输出目录为 `_quality-doc/{YYYYMMDD}_{需求名称}/`
- [ ] `test.md` 与 `accept.md` 均已落盘
- [ ] 元信息表含文档路径、关联 spec、关联 PRD、文档编号、生成时间

### 6.2 test.md

- [ ] 含 §1–§7 必选章节（§5 无相关内容时可写「本需求不涉及」）
- [ ] 满足 §3.3 派生硬约束（**第十章用例全覆盖**、场景、异常、写接口、事务/跨边界一致性）
- [ ] 每条用例「关联」含对应 `*UseCase#execute`（HTTP 用例含第十四章路由）
- [ ] 每条用例含 TC-ID、优先级、类型、前置、步骤、期望结果、关联
- [ ] 汇总表结果列留空，未伪造执行结果

### 6.3 accept.md

- [ ] 含 §1–§7 必选章节
- [ ] 范围与非目标已复述
- [ ] 每条 AC 含 AC-ID、业务表述、通过标准、演示路径、关联
- [ ] 验收结论区留空待人填写，未代填「通过」

### 6.4 边界

- [ ] 未修改 spec / audit / tasks / 业务代码
- [ ] 未写入自动验收命令、证据落点、通过率等执行态字段作为主内容
- [ ] 未把代码级集成测试规范内容复制成 `test.md` 主体
